# Yacht Booking Marketplace MVP — Full Implementation Plan

## Deep Reasoning Chain

### Why This Architecture
Replit provides an integrated environment where every infrastructure concern — database (PostgreSQL), authentication (Clerk), file storage (App Storage / GCS), payments (Stripe), and hosting (Autoscale + Mobile App) — is handled natively. This eliminates vendor sprawl and lets a single developer (aided by Replit Agent) build and ship the entire MVP without managing servers, SSL, or DevOps.

The Expo React Native mobile app connects to a Replit-hosted Express.js API. The admin dashboard is a web app served from the same backend. One project, one database, one deployment pipeline.

### Edge Cases Addressed in Plan
- **Payment succeeds but booking creation fails**: Use database transactions; PaymentIntent is created first, booking is created in same transaction, webhook reconciles any orphaned payments.
- **Concurrent bookings for same slot**: Database-level unique constraint on `(yacht_id, template_id, date, start_time)` with `CHECK (status NOT IN ('Cancelled', 'Rejected - Refunded'))` partial unique index.
- **Admin inaction on paid bookings**: Set a 24-hour SLA timer; if no action, escalate notification. Booking stays in review but guest gets reassurance messaging.
- **Host cancels availability after booking**: Availability slots are soft-deleted; existing bookings reference a snapshot, not the live slot.
- **Stripe webhook delivery failures**: Idempotency keys on all webhook handlers; reprocess on retry.

## Phase 4: Payments — Stripe Integration

### 4.1 Backend Payment Flow

```
Guest selects booking → 
Frontend calls POST /api/bookings (creates draft, status: pending_payment) → 
Backend creates Stripe PaymentIntent with amount in EGP → 
Returns clientSecret to frontend → 
Frontend opens Stripe Payment Sheet with clientSecret → 
Guest completes payment → 
Stripe webhook (payment_intent.succeeded) hits backend → 
Backend updates booking status to 'paid_under_review' → 
Backend updates payment record → 
Notification sent to admin and guest
```

### 4.2 Stripe Configuration

- Use Stripe Egypt (or international account with EGP support)
- Payment methods: Cards (Visa, Mastercard), Apple Pay, Google Pay
- PaymentIntent metadata stores: booking_id, guest_id, yacht_id
- Webhook endpoints:
  - `payment_intent.succeeded` → confirm payment
  - `payment_intent.payment_failed` → mark payment failed
  - `charge.refunded` → update refund status

### 4.3 Auto-Refund on Rejection

```
Admin rejects paid booking → 
Backend calls POST /v1/refunds with PaymentIntent ID → 
Stripe processes refund → 
Webhook (charge.refunded) confirms → 
Booking status → 'rejected_refunded' → 
Notification sent to guest
```

### 4.4 Fee Calculation (Server-Side)

```typescript
const PLATFORM_FEE_PERCENT = 0.20;
const baseAmount = yachtTemplatePrice; // what guest pays
const platformFee = baseAmount * PLATFORM_FEE_PERCENT;
const hostEarnings = baseAmount - platformFee;
```

All calculations happen server-side. Guest sees total. Host sees earnings. Admin sees full breakdown.

## Phase 6: Finance — Earnings, Holds, Payouts

### 6.1 Earnings Ledger

- Every confirmed booking creates an `earnings_ledger` entry
- Entry starts as `pending`, linked to booking
- After booking completion (`completed` status), entry becomes `available` after 3-day hold
- `eligible_at = completed_at + 3 days`

### 6.2 3-Day Hold Logic

```typescript
// Cron job runs daily (Replit Scheduled Deployment)
// For all bookings with status 'completed' and completed_at + 3 days <= now():
//   Update earnings_ledger status to 'available'
//   Update withdrawal_request eligibility
//   Send notification to host
```

### 6.3 Withdrawal Request Flow

1. Host sees available balance on earnings screen
2. Host taps "Request Withdrawal"
3. System shows available amount, eligible bookings breakdown
4. Host confirms → withdrawal request created (`withdrawal_requested`)
5. Admin reviews in dashboard
6. Admin processes manually (bank transfer outside system)
7. Admin marks as `paid` with reference number
8. Earnings ledger entries updated to `withdrawn`

### 6.4 Host Earnings Screen

- Available balance (after hold period)
- Pending balance (within hold period)
- Total earned (all time)
- Last payout info
- Earnings history list (per booking)
- "Request Withdrawal" button (enabled only if available balance > 0)

### 11.2 Middleware Stack

- `clerkAuth` — Validates Clerk JWT, attaches user to request

## Phase 12: Security Checklist

- [ ] All financial operations (PaymentIntent, refund) server-side only
- [ ] Stripe publishable key only in mobile app; secret key server-side only
- [ ] Raw card data never touches our servers (Stripe Payment Sheet handles this)
- [ ] Host documents stored in App Storage with admin-only access policies
- [ ] All admin actions logged in audit_logs
- [ ] Clerk JWT validated on every API request
- [ ] Role-based access enforced at API route level
- [ ] Input validation via Zod schemas on all endpoints
- [ ] Rate limiting on auth and booking endpoints
- [ ] HTTPS enforced on all API calls
- [ ] Environment variables for all secrets (Replit Secrets)
- [ ] SQL injection prevention via Drizzle ORM parameterized queries
- [ ] File upload validation (type, size limits)
